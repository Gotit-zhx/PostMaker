# PostMaker 产品目标与 MVP 范围

## 产品目标

PostMaker 面向科技内容创作者和小型内容团队，提供从行业素材到可审核、可追溯、多平台可适配内容草稿的工作台。核心价值是把 DataRadar 的信息采集与 PostMaker 的 persona 写作结合起来，让用户能理解素材来源、控制生成内容、编辑并决定是否采用。

产品不是通用聊天机器人，也不以无人审核的批量发文为目标。AI 负责整理和起草，人负责判断事实、修改和批准。

## 用户与主要场景

- 首要用户：经营科技/AI 内容账号的个人创作者，以及 2-10 人内容小组。
- 主要任务：发现值得跟进的素材，选择写作视角，生成草稿，核对来源，编辑并审核后导出。
- 主要问题：素材和生成结果分散；生成文章缺少审核状态和版本记录；难以回看引用来源与生成配置。

## 产品原则

1. **人工审核优先**：任何生成结果默认是草稿，不自动发布。
2. **来源可追溯**：草稿始终关联原始素材标题、平台和 URL；用户可以在编辑时查看素材摘要与原文。
3. **人设差异有边界**：persona 是写作视角和风格配置，不是冒充真实个人或虚构事实的许可。
4. **逐步验证价值**：先打通单用户的素材到审核闭环，再根据真实使用决定团队协作、发布和商业化投入。
5. **沿用现有资产**：继续使用 DataRadar API、Persona YAML、现有 LLM 生成器和 Markdown/HTML 输出能力。

## MVP 验收范围

### 必须具备

- 一个本地可运行的 Web 工作台，能显示 DataRadar 素材列表、来源和重要性信息。
- 按素材选择 persona 并生成草稿；显示加载、失败和空数据状态。
- 草稿列表可按审核状态筛选；草稿详情显示关联素材和来源链接。
- 用户可编辑标题和正文，并执行「待审核 / 已批准 / 已归档」状态流转。
- 每次保存都保留修订记录，可查看并恢复之前版本。
- 草稿与修订默认保存在本地 SQLite，不要求先配置 PostgreSQL。
- 从已批准草稿导出 Markdown；导出内容包含来源 URL、persona、状态和生成时间等元数据。
- AI API 未配置或 DataRadar 不可用时，界面给出可理解的错误提示，不伪造素材或生成成功状态。

### 暂不纳入

- 自动发布、浏览器模拟发布、绕过平台限制或批量账号操作。
- 用户注册、多租户、团队权限、云端托管和计费。
- 平台表现数据自动回收、复杂分析报表和模型自动训练。
- 完整事实核查保证。MVP 只保证素材来源可见，不宣称生成内容已核实。
- 新建独立采集引擎或替换 DataRadar。

## MVP 技术约束

- Web API 与静态工作台放在 PostMaker 包内，复用现有 Python 生成器和 DataRadar 客户端。
- 本地开发默认绑定 `127.0.0.1`，SQLite 数据放在 PostMaker 的 `output/` 下并可配置。
- API 边界使用 Pydantic 校验；SQLite 操作参数化；页面将用户/模型文本作为纯文本编辑，不直接注入 HTML。
- 生成调用保持可见的同步状态；MVP 暂不引入队列、Redis 或后台 worker。
- API Key 只从环境变量或现有配置读取，不在工作台页面回显。

## MVP 成功信号

用真实的科技内容工作流程完成至少一次完整闭环：找到一条素材、以 persona 生成草稿、检查来源、编辑、批准、查看修订并导出 Markdown。后续试用中关注：每周完成的审核草稿数、生成草稿采用率、平均编辑幅度、每篇成本/耗时、用户是否愿意连续使用。

## 后续路线（不作为 MVP 阻塞项）

1. 质量与成本度量：模型、token、耗时、失败原因、人工评分和改动幅度。
2. 来源引用与事实核查辅助：段落到来源片段映射、冲突提示和引用完整性检查。
3. 平台适配：按平台格式、长度和素材要求生成发布稿，先导出后评估官方 API。
4. 团队版：用户、角色、协作审核和共享 persona。
5. 商业验证：与科技创作者和小团队试用，验证持续使用频率和付费意愿后再决定托管 SaaS。

## 偏航检查

后续每项改动都应回答：它是否帮助目标用户更可靠地从可信素材走到人工批准的内容？是否保留人的审核责任？是否能用真实使用验证？若三个问题都不能肯定回答，应暂缓该改动。
