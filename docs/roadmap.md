# PostMaker 改造路线图

## 结论

PostMaker 最值得发展的方向不是继续做一个“输入主题、输出文章”的通用 AI 写作器，而是做成面向科技内容创作者和小团队的**可追溯内容生产与审核工作台**：DataRadar 负责发现和整理素材，PostMaker 负责 persona、生成、来源证据、人工编辑、质量检查和发布前适配。

这条路线能同时利用项目现有资产和形成差异化：素材来源、写作 persona、生成记录、人工修改、审核状态和最终成稿可以沉淀为一条完整的内容生产链。

## 调研得到的产品信号

1. 成熟的 AI 内容产品正在把竞争点从单次生成转向品牌语气、知识库和团队控制。Jasper 的 Brand Voice 支持从样例或 URL 建立写作风格，并将其用于工作区级别的生成；Jasper 也把品牌语气、受众、规则和知识组织成上下文层。
2. 企业级 AI 工作流越来越强调来源、决策记录、审计和人工审批。Writer 将 activity traces、source citation 和 decision logs 作为治理能力的一部分。
3. 生产级 AI 系统的技术竞争力来自可观测性和评估闭环。OpenAI 的 Agents 文档把 tracing、guardrails、focused evals 和 trace grading 作为持续改进工作流的基础。
4. 内容创作者仍需要独立核对原文。MLA 的 AI 使用指南明确建议作者点击并检查原始来源，不能把模型输出本身当作来源。

这些信号都支持当前产品目标：把人的判断放在审核环节，把 AI 用在素材整理、起草和检查，而不是把自动发布作为核心卖点。

## 方向评估

| 方向 | 商业价值 | 技术价值 | 与现有代码匹配度 | 建议 |
| --- | ---: | ---: | ---: | --- |
| 科技内容审核工作台 | 高 | 高 | 很高 | 立即做，作为主线产品 |
| 来源证据与事实核查辅助 | 高 | 很高 | 高 | 作为第一条差异化能力 |
| 多平台格式适配与发布准备 | 中高 | 中高 | 高 | 在审核闭环稳定后做 |
| 团队协作与共享 persona | 高 | 中高 | 中 | 取得 3-5 个试用团队后做 |
| 本地优先 / 私有部署版 | 中高 | 高 | 高 | 作为技术商业化选项 |
| 通用 AI 写作器 | 中 | 低 | 高 | 不建议作为定位 |
| 全自动无人审核发布 | 有短期吸引力 | 低且风险高 | 中 | 不作为主线 |

## 推荐主线：可追溯内容审核工作台

### 目标用户

- 个人科技、AI、开源领域创作者
- 2-10 人的内容小组或技术营销团队
- 需要自托管、保留数据控制权的研究团队或代理机构

### 核心承诺

用户可以从一条素材开始，在同一个工作区完成：

1. 了解素材来源、摘要、时间和重要性
2. 选择写作 persona 并生成草稿
3. 查看每个关键陈述对应的来源
4. 编辑、检查、批准并保留修订记录
5. 导出适合目标平台的发布稿

## 近期实现顺序

### P0：把 MVP 变成可使用的闭环

优先解决真实使用中的“可信”和“可观察”问题：

- 素材详情面板：正文摘要、来源 URL、发布时间、标签、重要性
- 草稿生成记录：模型、耗时、失败原因、生成参数、token 或成本估算
- 生成结果质量检查：标题长度、正文长度、空洞句、来源缺失、敏感或绝对化表述
- Markdown 导出元数据补充：素材 ID、来源、persona 版本、模型、生成时间、修订时间
- 明确的空状态和错误状态：DataRadar 不可用、AI 未配置、模型超时、返回格式错误

### P1：建立第一条技术壁垒——证据链

将草稿从“关联一篇素材”升级为“陈述可追溯”：

- 生成时要求模型返回结构化段落和 claims
- 每个 claim 保存来源 URL、来源片段和置信说明
- 编辑器中显示“有来源 / 待核对 / 与来源冲突”状态
- 导出时可选择内嵌引用、脚注或仅保留来源清单
- 对无法找到来源的陈述给出提示，不自动宣称已完成事实核查

建议的数据模型：`drafts`、`draft_revisions` 之外增加 `generation_runs`、`claims`、`claim_sources`。这样既能支持用户界面，也能为后续评估和审计提供数据。

### P1：建立第二条技术壁垒——生成评估闭环

- 保存每次生成的输入快照、persona 版本、模型、参数和输出
- 记录用户批准、退回、修改幅度和人工评分
- 建立 20-50 条真实素材的回归数据集
- 对来源完整性、事实一致性、风格匹配、重复率和编辑距离做离线评估
- 支持不同模型和 prompt 的 A/B 对比

这会让项目从“调用 LLM 的脚本”变成“有数据可优化的内容系统”。

### P2：平台适配层

先做导出适配，再考虑官方 API：

- 通用 Markdown
- 长文 HTML
- X / Threads 短帖
- LinkedIn 帖子
- Newsletter / 邮件正文

每个平台使用独立的约束配置：最大长度、标题规则、链接位置、标签格式、是否允许 Markdown。适配器应接收已批准内容，避免把平台规则混入生成核心。

### P2：团队版和私有部署

在确认有人持续使用后再增加：

- 用户、角色、审核人和评论
- 共享 persona、模板和来源库
- 工作区级配置与审计日志
- PostgreSQL、对象存储和后台任务
- Docker Compose 一键部署和备份恢复

商业上可以形成两种产品形态：个人创作者的低价托管版，以及内容团队/代理机构的团队版或私有部署版。

## 推荐的商业化顺序

1. **免费本地版**：保留当前 SQLite、本地运行和 Markdown 导出，用来获取真实反馈。
2. **专业版**：增加云端模型调用、来源证据、质量检查、平台适配和历史统计，按席位或生成额度收费。
3. **团队版**：增加共享工作区、审批、权限、评论、审计和统一 persona。
4. **私有部署版**：为对数据敏感的公司、代理机构和研究团队提供 Docker/Kubernetes 部署、模型自带或自定义 API、备份和支持服务。

不建议一开始做 SaaS 计费、复杂多租户或自动发布。它们会提前引入账户、权限、支付、队列和平台合规成本，而当前最需要验证的是用户是否愿意持续使用“发现素材 → 审核 → 发布准备”这条链路。

## 成功指标

先跟踪能判断产品价值的指标：

- 每周完成的已批准草稿数
- 生成草稿被采用的比例
- 从生成到批准的平均时间
- 人工编辑字符比例和退回原因
- 每篇生成成本与失败率
- 用户点击来源并完成核对的比例
- 一周后仍继续使用的创作者或团队数

商业验证阶段至少找 3-5 位创作者或 1-2 个小团队，连续使用两周，再决定是否投入团队协作和托管服务。

## 下一步执行清单

1. 用真实 DataRadar 数据跑通一次完整闭环。
2. 在工作台加入素材详情和生成运行记录。
3. 把生成输出改成结构化结果，为 claims 和来源映射留接口。
4. 增加 20-50 条回归素材和人工评分字段。
5. 让 3-5 位目标用户试用并记录退回原因。
6. 根据真实反馈决定优先做证据链、平台适配还是团队协作。

## 偏航检查

每项新功能都应回答三个问题：

- 是否让用户更可靠地从来源走到已批准内容？
- 是否让人工判断更快、更清楚，而不是隐藏判断过程？
- 是否能通过真实使用数据验证改进效果？

不能回答“是”的功能暂缓。
